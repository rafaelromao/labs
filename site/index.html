22 labs · Java + Go · tests included

Twenty-two backend components, each with a test suite.

Each lab is a small production-style component (a blocking queue, a rate limiter, an outbox, a route planner) with a written contract, a diagram, a starter stub in Java and in Go, and a test suite that checks the contract. You implement the stub until the tests pass, then compare with the reference solution.

Why work against supplied tests

Tests you write yourself mostly confirm what you already believed. A supplied suite does the opposite: it fails on the boundary you skipped, the tie you broke differently, or the interleaving you never imagined. Reading the reference only after your own attempt fails or passes is where most of the learning happens, so the order below matters more than the code.

Four steps per lab

  1. Read the contract and the tests.
    Open the lab page and its test file. List inputs, outputs, boundaries, invariants, failure behaviour and resource limits.
  2. Implement the starter.
    Replace every TODO in the stub. Run the lab's tests and fix what fails before reading anything else.
  3. Compare.
    Open the reference solution and explain one representation or synchronization difference, and whether your version still keeps the contract.
  4. Change something.
    Add a test for an edge case you chose, or implement the variation suggested on the lab page.

Open and run

The repository holds two IntelliJ IDEA projects. Open java/ (Gradle, Kotlin DSL, JDK 21 — Gradle downloads it if missing) or go/ (Go 1.25+, with the Go plugin or GoLand; CGO and a C compiler are needed for the SQLite labs). Each project includes an All labs run configuration, and every test has a gutter run icon. From a terminal:

cd java
./gradlew test
./gradlew test --tests 'labs.ttlcache.*'

cd go
go test -race -count=1 ./...
go test -race -count=1 ./ttlcache

Start with L05 TTL cache if you have not done this before: it combines capacity, recency, time and shared state in one small class, and its tests show the shape the other labs expect — an injected clock, an inclusive deadline and a concurrent schedule.

Supporting code

The starters ship two helpers fully implemented: algorithms/Structures (indexed heap, trie, interval merge, union-find, top-K, Fenwick and segment trees, Bloom filter, and more) and the haversine distance in the nearby-search lab, which the geofence and trajectory labs reuse. solutions/ also contains supporting examples that are not labs:

  • spatial — exact planar integer predicates, a quadtree and versioned fence replacement, with the shared fixture fixtures/polygon.tsv.
  • fencing, cells, httpio — stale-owner rejection with fencing tokens, H3/S2 cell round trips, bounded HTTP bodies with controlled deadlines.
  • postgres — a READ COMMITTED adapter and a one-batch relay. Integration-only: start the disposable PostGIS with docker compose up and run ./gradlew integrationTest in solutions/java.

Where the tests stop

A green suite is evidence about the cases someone wrote, not proof over every schedule. The components are local and in memory unless a lab says otherwise; clocks are injected, so real wall-clock drift is untested; and mutable values are not deep-copied. When you discuss production readiness, say which limit you would test next rather than claiming the suite covers it. A few Go tests in solutions/go also inspect internal fields; the starter versions check the same behaviour through the public API so that your design stays your own.
